# IE_HW1_40131038 (GIT)

## سوال اول
هر دو دارن تغییرات یه برنچ رو ترکیب میکنن با یه برنچ دیگه اما مدلی که این کارو انجام میدن با هم فرق داره.

زمانی که شما یه برنچ رو مرج می کنید، گیت یه کامیت جدید میسازه که دو تا parent داره:
1. اون برنچی فعلی مون که توش هستیم
2. اون برنچی که قراره مرج بشه.

اما rebase یه فراینده از ترکیب کردن یه بخشی از کامیت ها با یه base commit جدید. این بهت اجازه میده که تغییرات یه برنچ رو برداری و بذاری سر برنچ دیگه.

یعنی توی rebase میتونیم کل برنچ مون رو برداریم و اون رو در ادامه ی برنچ main مون بذاریم.

زمانی بخوایم هیستوری هر دو برنچ مون رو داشته باشیم یا دو تا برنچ مون رو یکپارچه کنیم و کانفلیکت های 2 برنچ رو پیدا کنیم استفاده از merge گزینه بهتریه.
اما زمانی که میخوایم کامیت هامون خطی باشن و code review و دیباگ کردن رو راحت تر کنیم میریم سراغ rebase.

## سوال دوم
زمانی که از دستور
```bash
git diff
```
استفاده می کنیم، به اون جاهایی از فایل که چند خطشو اضافه/حذف/ویرایش کردیم میگن **hunk**. مثل این هم نشون داده میشه:
```git
@@ -10,5 +10,7 @@
```
این داره نشون میده که این تغییرات از کجا شروع شده و چند خط تغییر کرده بین نسخه قدیمی و نسخه جدید.

برای بررسی تعاملی هم می تونیم از دستور زیر استفاده کنیم:
```bash
git diff file1.go
```
بعدش از دستور زیر استفاده می کنیم که بتونیم از hunk رو جداگانه بررسی کنیم:
```bash
git add -p file1.go
```
> -p یا --patch اجازه میده بهمون که هر هانک رو جداگانه بررسی کنیم.

با استفاده از گزینه های زیر هم میتونیم اون هانک هایی که میخوایم رو انتخاب کنیم:
| گزینه | کاربرد |
|     :----:    |     :----:    |
| y | اضافه کردن هانک فعلی به staging |
| n | اضافه نمی کنه هانک فعلی مونو به استیجینگ |
| s | هانک مون رو تقسیم می کنه به بخشای کوچک تر اگه امکانش باشه |
| e | ویرایش دستی patch برای این که دقیق تر خط ها رو انتخاب کنیم |
| q | خارج میشه |
| ? | راهنما رو نشون میده |

در گام پایانی هم میشه اون هانک هایی که استیج کردیم رو با دستور زیر دوباره بررسی کنیم:
```bash
git diff --cached
```
و بعدش هم که می تونیم کامیت کنیم اونایی که اسیتج شدن رو.

فایده این کار (partial staging) میشه اون تغییرای نامرتبط توی یه فایل رو توی کامیتای جداگونه ثبت کرد.

این جوری:
- هر کامیت ممون تغییراتش atomic تر میشن
- هم code review مون راحت تر میشه
- و rollback کردن مون هم اسون تر و ساده تر میشه

## سوال سوم
دستور 
```bash
git bisect
```
برای پیداکردن اون کامیتیه که یه باگ درست کرده. میاد با binary search کامیت ها رو بررسی میکنه  تا باگ رو پیدا کنه.
برای شروع سرچ از دستور زیر استفاده میکنیم:
```bash
git bisect start
```
گام دوم باید کامیتی که باگ داره رو مشخض کنیم. این دستور کامیت فعلی مون رو باگ دار اعلام میکنه:
```bash
git bisect bad
```
توی گام بهدی باید یه کامیت سالم مونو مشخص کنیم. توی این گام گیت میدونه میدونه باگ بین دو تا کامیت سالم باگ دار (خراب) ایجاد شده:
```bash
git bisect good <commit-hash>
```
توی گام چهارم گیت میاد به صورت خودکار یه کامیت از کامیتای بین  کامیت خراب و کامیت سالمی که مشخص کردیم رو checkout میکنه و کدمونو آزمایش میکنه:
- اگع خطا وجود داشت: git biscet bad
- اگه خطا وجود نداشت: git bisect good
(میاد دامنه جست و جو رو کوچیک میکنه تا اولین کامیتی که باگ رو درست کرده برسه.)
بعد از چندین بار تکرار این گام اولین کامیت باگ دارمون رو پیدا میکنه و با استفاده از دستور زیر میایم از حالت bisect خارج میشیم (معمولا به برنچ یا وضعیت قبلی مون برمیگردیم بعدش):
```bash
git bisect reset
```

کاربردش مثلا میشه جایی که یه پروژه ای داریم با کلی کامیت و بعد از اپدیت کردن یه بخشی دیگه اون بخش کار نمیکنه و نمیدونیم دقیقا مشکل از کجاست. توی این حالت استفاده از bisect خیلی بهمون کمک میکنه چون به خاطر استفاده از باینری سرچ پیچیدگیش *O(log n)* عه.

## سوال چهارم
### بخش 1
---
برای وضعیت ریپو:
```bash
git status
```
برای تغییراتی که stage نشدن:
```bash
git diff
```
برای stage شده ها:
```bash
git diff --staged
```
یا
```bash
git diff --cached
```

تفاوتی که *diff* و *diff --cached* دارن اینه که:
- diff داره تغییرات بین محیط کارمون (جایی که داریم دولوپ میکنیم کدمونو) و چیزایی که stage کردیم رو نشون میده
- diff --cached میاد تغییرات بین فایلای استیج شده و هد رو نشون میده

### بخش 2
---
فقط اون فایلایی که قبلا استیج شدن کامیت میشن. اونایی که قبلا با
```bash
git add <filename>
```
استیج شون کردیم.
با این وضعیت یعنی فایلای untracked دایرکتوری tmp/ هم کامیت نشدن.
چون گیت زمانی که
```bash
git add
```
رو میزنیم میاد یه snapshot از محتوای فایلامون که استیج شدن میگیره. اگه بعد از این، اون فایلا رو ویرایش کنیم تغییرات جدیدمون توی snapshot نیستن.

### بخش 3
---
برای این که فایلای دایرکتوری tmp/ هم کایمت نشن باید بریم سراغ *.gitignore*. توش باید بنویسیم:
```text
/tmp/*
```
این جوری فایلای دایرکتوری tmp/ ایگنور میشن.

البته اینم بگم که *.gitignore* فقط روی فایلای untrackedاثر داره و اگه فایلی رو قبلا وارد استیج کرده باشیم اول باید با دستور
```bash
git rm --cached path/to/file
```
فایل رو بدون این که از سیستم حذف کنیم، از بین فایلای track شده بکشیم بیرون.

## سوال پنجم
### بخش 1
---
زمانی که دو نفر میخوان یه بخش مشترک رو به شکلای متفاوتی تغییر بدن، git نمیتونه خودش تصمیم بگیره که کدوم تغییرو نگه داره و کدوم رو دور بریزه و این جا merge conflict رخ میده.
لزوما هم هر تغییری توی بخشای مشترک باعث merge conflict نمیشه. اگه این تغییرا مثلا مستقل از همه دیگه باشن یا مثلا با هم تداخل نداشته باشن گیت خودش میاد مرج میکنه.

### بخش 2
---
دوباره برای وضعیت فایلا:
```bash
git status
```
و برای این که فقط اسم فایلایی که کانفلیکت دارن رو ببینیم:
```bash
git diff --name-only --diff-filter=U
```
> [!NOTE]
> اینو از GPT پرسیدم کامندشو

توی جوابش گیت میاد اون جاهایی که کانفلیکت داره رو با conflict markers مشخص میکنه

### بخش 3
---
اول باید بریم روی برنچ main:
```bash
git switch main
git merge description-feature
```
اگه کانفلیکتی وجود داشت، گیت خودش میاد مرج رو متوقف میکنه.
توی گام بعدی باید کانفلیکتو ببینیم:
```bash
git status
git diff
```
گام سوم باید فایلی که کانفلیکت داره رو دستی باز کنیم و تغییرات توش رو باید یکی کنیم. بعدش باید conflict marker ها مثل:
- <<<<<<<
- =======
- \>>>>>>>

رو حذف کنیم.

گام چهارم میام دوباره چک میکنیم کانفلیکتی نمونده باشه:
```bash
git diff --check
```
(دستی هم میتونیم بررسی کنیم)

گام بعدی میایم فایلی که درستش کردیم رو استیج میکنیم و بعدش مرج مون رو کامل می کنیم:
```bash
git add README.md
git commit
git merge --continue
```

> این بخشو از GPT پرسیدم و از روش خوندم و اینو نوشتم

اگه بخوایم وسط یه مرجی اون مرج رو کنسل کنیم و ریپو رو به حالت قبل از مرج برگردونیم باید از این دستور استفاده کنیم:

## سوال ششم
### بخش 1
---
برای حذف تغییرایی که توی فایل notes.txt دادیم اما هنوز استیج نشدن:
```bash
git restore notes.txt
```
زمانی که این کارو انجام بدیم:
- working tree: تغییرای فایل حذف میشن و محتواش میشه همون محتوایی که زمان استیج شدن و اون snapshot بود
- staging area: بدون تغییر باقی میمونه
- commit history: تغییری نمیکنه
- فایلای دیگه هم دست نخورده باقی میمونن.

چون نسخه staging با اخرین کامیت (head) یکیه فایل به اخرین نسخه کامیت شده برمیگرده.

### بخش 2
---
اگه فایلو اشتیاهی استیج کرده باشیم:
```bash
git restore --staged notes.txt
```
زمانی که این کارو انجام بدیم:
- working tree: تغییرای فایلا حفظ میشن
- staging area: فایل به اخرین نسخه کامیت (head) برمیگرده و تغییراش از staging خارج میشه
- commit history: تغییری نمیکنه

پس تغییرا هم از حالت staged به unstaged تبدیل میشن.

### بخش 3
---
چون کامیت اشتباه قبلا پوش شده و بقیه تیمم اونو دریافت کردن باید از این دستور استفاده کنیم:
```bash
git revert <commit-hash>
git push origin main
```
زمانی که این کارو انجام بدیم:
- working tree: اثر تغییرای کامیت اشتباه معکوس میشن
- staging area: بعد از این که کامل revert شد، توی حالت عادی clean عه
- commit history: یه کامیت جدید ایجاد میکنه که اثر کامیت اشتباه رو خنثی کنه و کامیت قبلی هم حذف میشه

این که *git reset* یا *git push --force* مناسب نیستن هم اینه که چون هستوری برنچ های مشترک رو میان بازنویسی میکنن و ممکنه که بازم کانفلیکت درست کنن و غیر از اون ممکنم هست باعث ناسازگاری با ریپوی بقیه تیم بشن. اما *git revert* هیستوری رو حفظ میکنه و برای برنچای مشترک روش امن تریه.

> این بخشو از GPT پرسیدم و از روش خوندم و اینو نوشتم
